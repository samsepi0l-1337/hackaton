## 6. 멘토의 해커톤 방법론

### MVP와 린 방식

- 스타트업이 망하는 가장 큰 이유: 아무도 원하지 않는 제품. 문제가 실제로 있는지, 해결책이 도움이 되는지 검증한다. [16:58, 17:56]
- 다 만들고 합치지 말고, **처음 1시간 안에 동작하는 것**을 만든 뒤 기능을 하나씩 추가한다. Done is better than perfect. 하드코딩도 괜찮다. [16:00, 19:54]
- 만들고 → 가설 검증 → 맞으면 기능 추가, 틀리면 피벗. [21:51, 22:50]
- 처음 5명 정도에게 직접 피드백을 받는다. 참가자 약 100명을 활용할 수 있다. [23:49]
- 아이디어는 숨기지 말고 공유한다. 공유할수록 발표 호응이 높다. [14:08, 15:03]

### AI 활용

- AI는 불필요한 기능을 늘리기 쉽다. 핵심 기능만 남기고 **한 번에 기능 하나**만 시킨다. [32:18, 37:13]
- 구현은 AI가 대부분 해주므로 점수 차이가 작다. **문제 정의와 솔루션 매칭**이 점수를 가른다. [35:50]
- 팀 내에서 문제와 솔루션을 충분히 논의한 뒤 AI에게 맥락을 준다. [36:21]
- 커밋을 자주 한다 (AI가 코드를 지우거나 덮어쓰는 경우 대비). [46:45]

### 수상 준비 [38:13, 39:15]

- 심사표의 주제와 아이디어가 맞아야 한다. 재미만을 위한 아이디어는 피한다.
- 동남권 특성에 맞춰 **고객이 누구이고 어떤 불편을 어떻게 해결하는지** 명확히.
- 역할 분담: 개발, 조사, 인터뷰, 발표 준비.

### 발표 [41:04 – 44:53]

- 두괄식: 첫 문장에 "누구의 어떤 문제를 어떻게 해결하는지".
- 사용자 테스트 결과와 개선 과정을 **수치로** 제시.
- 기술 스택·팀 소개·개발 과정보다 문제와 해결에 집중.
- 대본을 읽지 말고 키워드 3개와 첫 문장만 외운다. 프레젠터를 미리 눌러 본다.

### 시연 [45:51 – 48:39]

- 질문에는 "맞습니다/아닙니다"로 먼저 답한다.
- 실패 대비 **백업 영상** 준비, 문제 시 즉시 전환.
- 로그인·회원가입 생략, **테스트 계정**으로 핵심 기능부터.
- 사람이 많으면 Wi-Fi 간섭이 있으니 현장에서 다시 확인.

### 배포 [48:39 – 52:44]

- **공개 URL로 배포**해 실제 사람에게 보여주고 피드백을 받는다.
- API 키를 공개된 곳에 올리지 않는다 (토큰 과금 공격).
- 팀페이지를 풍부하게 채운다 (심사에 반영). 동시 편집은 한 번에 한 명.
